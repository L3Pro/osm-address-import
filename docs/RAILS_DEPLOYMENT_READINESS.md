## iD initialization diagnosis

The test used the same production Rails build, synthetic login, OAuth configuration and CSP for a blocked run and a fixture-enabled run. The only functional difference was a private, test-only mapping of iD data requests to exact package files served over the same loopback TLS origin. The browser's external HTTP(S) proxy pointed at a closed loopback port, the disposable Docker network remained internal, and the TLS proxy rejected every mutation except login. No production OSM API request was possible through that path.

## External dependency decision

**Use iD's existing upstream CDN requests for this candidate.** The controlled Firefox run proved that allowing only jsDelivr, with no URL remapping or local mirror, restores the complete editor and read-only interactions. The earlier pinned fixtures established an offline diagnostic path, but no evidence now requires shipping them. A local bundle would add a package-update, integrity, licensing, asset-build and cache-invalidation workflow to maintain. The [upstream iD API](https://github.com/openstreetmap/iD/blob/develop/API.md) describes the externally sourced presets and name-suggestion data.

| Approach | Evidence and operational effect |
| --- | --- |
| Existing upstream requests | Passed authenticated Firefox initialization and read-only interaction with only `cdn.jsdelivr.net:443` allowed. Preserves upstream iD behavior and its CDN caching; browser access to that destination is required. |
| Reviewed local copies | Pinned schema and name-suggestion fixtures passed the earlier isolated test. This is a viable fallback for clients that cannot reach the CDN, but it needs a separately reviewed integration and update policy. It is not part of PR #19. |

The Rails asset build pins `@openstreetmap/id` **2.41.0** in Yarn with SHA-512 integrity. Its runtime requests tagging schema `@^6.18.0` (resolved to 6.19.2 in this test) and name-suggestion index `@~7.2` (resolved to 7.2.20260530). The schema package lookup uses a moving alias, then exact-version data URLs; name-suggestion data URLs retain the range alias. The observed alias responses permitted cross-origin reads and had a seven-day browser cache lifetime; exact schema data had a one-year immutable lifetime. The first run transferred 3,279,849 bytes for the 15 critical resources, while a true refresh transferred zero bytes. [jsDelivr documents its alias and exact-version caching](https://github.com/jsdelivr/jsdelivr#caching). Independent curl through the same allowlist proxy verified CDN TLS. iD's runtime `fetch(url)` does not check a content hash or SRI for these JSON responses, and a range alias can advance without a Rails deployment. If the schema request fails, the current iD build leaves a blank editor without a visible recovery message. Record CDN failures as a release/rollback signal rather than treating the HTML iframe as a successful editor check.

Cloudflare Access protects the configured Osaka application hostname; iD's jsDelivr requests leave the user's browser separately. The controlled test shows that a browser able to reach `cdn.jsdelivr.net:443` can initialize the editor, but it does not prove that every intended user's network, Gateway policy or remote browser allows that destination. Check an authorized Access browser path before traffic cutover. Keep the CDN destination narrowly allowlisted where browser egress is controlled. Bing imagery, OSM tiles, Taginfo, Nominatim, osm-community-index and WMF services were not established as editor-critical in this run; imagery, search and these integrations need separate functional checks as applicable.

## Risks found and corrected in PR #19

The original draft would start a side-by-side candidate with the existing database role and storage volume writable before route approval. The base Compose file now mounts storage read-only and sets PostgreSQL's transaction default to read-only; a separate `compose.cutover.yml` override enables writes only after explicit cutover approval. **This is an operational guard, not a database privilege boundary:** the existing role retains write privileges and application code could change a session setting. The candidate was not connected to the original DB during this audit. [PostgreSQL documents `PGOPTIONS` as a per-session default](https://www.postgresql.org/docs/14/config-setting.html), and [Docker Compose documents read-only mounts and override merging](https://docs.docker.com/compose/how-tos/multiple-compose-files/merge/).

The tunnel helper previously accepted arbitrary config paths, could overwrite a config changed while it validated, and inherited the live file's 0644 mode. It now restricts its live target, uses a private lock for cooperating invocations, checks content/inode/mtime before replacement, sets mode 0600, retains a mode-0600 backup, and refuses automatic rollback after unrelated edits. A non-cooperating editor could still race in the final check/replace interval; prohibit concurrent tunnel-config edits during the approved maintenance window. The live file remains unchanged and currently has mode 0644. A tunnel restart is a separate step; if it fails, restore the prior route and restart the old tunnel before leaving the window.

The existing app has no configured shared memcache session store. Its sessions live in process memory, so cutover requires re-login; a rollback after a candidate login may also require re-login. The isolated test proved synthetic login and OAuth token reads, but did not prove continuity for current users. After cutover, normal account, OAuth, and uploaded-file writes to shared resources would persist across a route rollback. The old web must remain available throughout the rollback window.
