# Issue #15: production Rails deployment readiness audit

**2026-11-10 — restricted-role technical GO on an isolated restore; NO-GO for original-DB provisioning, side-by-side startup or cutover.** The prior preflight stopped because its database identity could write. A separate role, candidate-IP authentication guard and private credential are now implemented and tested only on a disposable restored database. No role, HBA file, storage mount, tunnel, original service or OSM object was changed on Osaka. Applying the database changes requires separate approval.

## 2026-11-10 restricted-role isolated validation

The verified 81,593,015-byte Osaka archive restored into a project-labeled PostgreSQL container on an internal network with its own volume and no host port. Restored counts matched the original audit: 1,865,425 nodes, 364,226 ways, 4,350 relations, 1,146,865 way tags, 35 users, 9 OAuth access tokens and 4 OAuth applications. Production assets were built in a private source copy with Docker networking disabled. The separate preflight credential was generated into mode-0600 private files; no secret was committed.

The provisioner creates `osm_rails_preflight_ro` with LOGIN, no superuser/database/role/replication/bypass-RLS privileges, no inherited role membership and a connection limit of eight. It grants CONNECT, schema USAGE and SELECT on nine public OSM tables plus a four-column `issue15_preflight.users` view. It grants no SELECT on the underlying `public.users` table, no sequence rights, table mutation rights or OAuth-table read rights. PostgreSQL 14's existing PUBLIC grants would otherwise allow schema CREATE, database TEMP and SELECT on three PostGIS metadata relations; the procedure revokes those grants. This changes shared database ACLs and must be reviewed before original-DB execution. Rails queries `users.*` for map rendering: a column-only table grant returned 500, while a three-column view failed primary-key discovery. The tested four-column view exposes only `id`, `display_name`, `data_public` and `creation_time`; a preflight-only initializer supplies the view's `id` primary key. Writable cutover disables that initializer and uses the original table.

The original database's host authentication policy alone would not bind a candidate to the restricted identity. The tested HBA helper prepends a SCRAM rule for that role from one fixed candidate IP, immediately followed by a reject rule for all other roles from that IP. It retains an exact mode-0600 backup, verifies rule order, refuses unexpected project/network ownership, and supports an exact-content rollback. On the disposable restore, install, repeated install, rollback and reinstall passed. A separate future cutover environment and IP are kept outside this preflight guard; live network details remain in the private audit.

From the guarded IP, all nine public-table SELECTs and the user-view SELECT passed. INSERT, UPDATE, DELETE, TRUNCATE, schema/temporary/database DDL, role creation and `SET ROLE` failed even after explicitly turning the session's read-only default off. Reads of the underlying users table, OAuth tokens, migration metadata and PostGIS metadata failed; the view lacked email and password-hash columns. A wrong password failed SCRAM authentication and a superuser login attempt hit the HBA reject rule. The provisioner ran repeatedly without changing its intended privilege set. Production Rails became healthy; unauthenticated capabilities, root, Box A map, node, way, relation and compiled iD JS/CSS returned 200, while unauthenticated `/edit?editor=id` and `/id` redirected as expected. Box A remained 336,634 bytes with SHA-256 `5825621a1c170becd85cdbe6db13498bc7d3d3f31400e44c6e9581ccb9155739`. Disposable OSM/user/OAuth counts stayed unchanged. This does not test authenticated editor or live Access behavior under the restricted role.

The exact role, PUBLIC ACL and HBA changes for Osaka are in the [rollout runbook](RAILS_PRODUCTION_ROLLOUT.md#restricted-database-provisioning-requires-separate-approval). That approval would authorize database provisioning only. A renewed side-by-side launch approval, then a separate writable cutover approval, remain required.

This preflight did not make those changes or render a configuration containing live secrets. The candidate did not run, so there are **no new side-by-side latency, response-byte, error or memory measurements**. The previous isolated benchmark and browser results below remain valid only for their disposable environments.

The isolated role, credential, HBA guard and Compose changes described above now resolve the technical design work requested by that stop. Before another original-DB launch attempt, obtain separate approval for the role/PUBLIC ACL/HBA changes, then recheck backup freshness, host headroom, source/image revisions, mounts, network, rollback and original counts. The Cloudflare Access browser path, external imagery, session re-login and post-cutover write semantics remain cutover blockers. Never use the existing superuser identity for the read-only side-by-side candidate.

## External dependency decision

**Use iD's existing upstream CDN requests for this candidate.** The controlled Firefox run proved that allowing only jsDelivr, with no URL remapping or local mirror, restores the complete editor and read-only interactions. The earlier pinned fixtures established an offline diagnostic path, but no evidence now requires shipping them. A local bundle would add a package-update, integrity, licensing, asset-build and cache-invalidation workflow to maintain. The [upstream iD API](https://github.com/openstreetmap/iD/blob/develop/API.md) describes the externally sourced presets and name-suggestion data.

| Approach | Evidence and operational effect |
| --- | --- |
| Existing upstream requests | Passed authenticated Firefox initialization and read-only interaction with only `cdn.jsdelivr.net:443` allowed. Preserves upstream iD behavior and its CDN caching; browser access to that destination is required. |
| Reviewed local copies | Pinned schema and name-suggestion fixtures passed the earlier isolated test. This is a viable fallback for clients that cannot reach the CDN, but it needs a separately reviewed integration and update policy. It is not part of PR #19. |

The Rails asset build pins `@openstreetmap/id` **2.41.0** in Yarn with SHA-512 integrity. Its runtime requests tagging schema `@^6.18.0` (resolved to 6.19.2 in this test) and name-suggestion index `@~7.2` (resolved to 7.2.20260530). The schema package lookup uses a moving alias, then exact-version data URLs; name-suggestion data URLs retain the range alias. The observed alias responses permitted cross-origin reads and had a seven-day browser cache lifetime; exact schema data had a one-year immutable lifetime. The first run transferred 3,279,849 bytes for the 15 critical resources, while a true refresh transferred zero bytes. [jsDelivr documents its alias and exact-version caching](https://github.com/jsdelivr/jsdelivr#caching). Independent curl through the same allowlist proxy verified CDN TLS. iD's runtime `fetch(url)` does not check a content hash or SRI for these JSON responses, and a range alias can advance without a Rails deployment. If the schema request fails, the current iD build leaves a blank editor without a visible recovery message. Record CDN failures as a release/rollback signal rather than treating the HTML iframe as a successful editor check.

Cloudflare Access protects the configured Osaka application hostname; iD's jsDelivr requests leave the user's browser separately. The controlled test shows that a browser able to reach `cdn.jsdelivr.net:443` can initialize the editor, but it does not prove that every intended user's network, Gateway policy or remote browser allows that destination. Check an authorized Access browser path before traffic cutover. Keep the CDN destination narrowly allowlisted where browser egress is controlled. Bing imagery, OSM tiles, Taginfo, Nominatim, osm-community-index and WMF services were not established as editor-critical in this run; imagery, search and these integrations need separate functional checks as applicable.

## Risks found and corrected in PR #19

The original draft would start a side-by-side candidate with the existing database role and storage volume writable before route approval. The base Compose file now mounts storage read-only and sets PostgreSQL's transaction default to read-only; a separate `compose.cutover.yml` override enables writes only after explicit cutover approval. **That transaction default alone is an operational guard, not a database privilege boundary:** the existing role retains write privileges and application code could change a session setting. The new restricted role plus candidate-IP HBA rules supply the tested database boundary in the isolated restore. No candidate has connected to the original DB. [PostgreSQL documents `PGOPTIONS` as a per-session default](https://www.postgresql.org/docs/14/config-setting.html), and [Docker Compose documents read-only mounts and override merging](https://docs.docker.com/compose/how-tos/multiple-compose-files/merge/).

The tunnel helper previously accepted arbitrary config paths, could overwrite a config changed while it validated, and inherited the live file's 0644 mode. It now restricts its live target, uses a private lock for cooperating invocations, checks content/inode/mtime before replacement, sets mode 0600, retains a mode-0600 backup, and refuses automatic rollback after unrelated edits. A non-cooperating editor could still race in the final check/replace interval; prohibit concurrent tunnel-config edits during the approved maintenance window. The live file remains unchanged and currently has mode 0644. A tunnel restart is a separate step; if it fails, restore the prior route and restart the old tunnel before leaving the window.

The existing app has no configured shared memcache session store. Its sessions live in process memory, so cutover requires re-login; a rollback after a candidate login may also require re-login. The isolated test proved synthetic login and OAuth token reads, but did not prove continuity for current users. After cutover, normal account, OAuth, and uploaded-file writes to shared resources would persist across a route rollback. The old web must remain available throughout the rollback window.
